01 — How We Approached This Review

Reviewed as a first-time user, not as a designer

Rather than treating this as a visual redesign exercise, the platform was navigated as a new user would, with no prior briefing. Every finding below is framed through the three core jobs your users need to do. Everything flagged is a place where the current design creates friction, ambiguity, or confusion in one of these three jobs.

The scope is intentional: practical design improvements to existing functionality. No new prototypes. No stablecoin or wallet complexity. Focus on reducing ambiguity, improving user efficiency, and helping users understand how the platform works.

Job 01

Log billable work

Quickly and accurately, for the right project and the right person.

Job 02

Get paid

Understand what is owed, when, and how to receive it.

Job 03

Pay a team

Understand what each person is owed, action it confidently, and have a record of it.

02 — Section 1: Core Workflow Observations

Three friction points in the core payment loop

1

1.1 — The work entry mechanics are sound. The mental model is not.

The work entry form is structurally sound. The contextual placeholder text change is a genuinely good UX detail. However, a new user arriving at a blank project screen has no way of knowing what the form does, what happens when they submit, or what the "Custom amount" dropdown is for.

The problem: Every project screen for every new user is an empty slate with no explanation. There is no example entry, no onboarding prompt, and no visual indication of what a completed work log looks like. Users are expected to figure out the workflow through trial and error.

The opportunity: Contextual empty states that teach as they guide. The first time a user lands on a blank project, the screen should show a simplified, illustrated version of the completed workflow: here is what a logged work entry looks like, and here is how it becomes a payment.

Wireframe Priority: High No new screen required
2

1.2 — Crypto-first visual hierarchy creates hesitation before trust is established

The platform presents three top-up options (USDC stablecoin, USD wire, EUR SEPA) with equal visual weight. For a user with no intention of using stablecoin, the presence of crypto terminology in a financial platform creates immediate hesitation. It signals complexity and risk before the user has understood the product's core value.

The problem: The platform's identity is unclear at the wallet level. Is this a crypto-first product or a traditional payment product that also supports crypto? The current design suggests the former, even if the business intent is the latter.

The opportunity: If bank transfer and SEPA are the primary intended routes, they should lead the UI. The stablecoin option should be secondary, clearly labelled as an advanced option, or accessible only via a disclosure toggle. This is a hierarchy decision, not a feature removal.

Wireframe Priority: Medium Modal redesign only
3

1.3 — The highest-stakes action in the platform has no confirmation step

The "Pay All" button is the highest-stakes action in the entire platform. It should communicate clearly: who is being paid, how much, from which balance, and give the user a confirmation step before anything is executed.

Currently, the button is always active and always silent. Clicking it with a zero balance produces no response whatsoever. There is no confirmation modal, no summary of what will happen, and no feedback that the action was received.

"On a payment platform, silent actions on financial buttons are unacceptable. This is not just a usability problem. It is a trust problem."

The opportunity: A payment confirmation modal that shows contractor name(s), amount owed per person, total amount, source wallet/account, and a clear "Confirm payment" CTA. Even a basic version of this would dramatically increase user confidence.

Wireframe Priority: Critical Core transaction flow
03 — Section 2: Missing Views and Features

Three structural gaps that limit power-user utility

The following are gaps that go beyond fixing existing screens. These are structural missing pieces that would significantly improve user clarity.

2.1 — Missing: Financial Overview Across Projects and People

Currently, a user who manages multiple projects and multiple contractors has no way to see a consolidated financial picture. There is no screen that answers:

  • How much have I paid out this month across all projects?
  • How much is currently outstanding across all contractors?
  • What is the payment history for a specific contractor across projects?
  • What is the financial summary for a specific project over time?

This is the single most significant missing feature from a user efficiency standpoint. Power users managing several contractors will quickly outgrow a per-project view and will need this consolidated layer.

Suggested screen: A Financials or Overview tab at the top level (not inside a project) showing total outstanding, total paid with date filter, a breakdown by project, and a breakdown by contractor. This can be a simple table at first.

Wireframe Priority: High

2.2 — Missing: Project Role Clarity — Owner vs. Contributor

The current navigation shows all projects in the same sidebar list with identical visual treatment. There is no distinction between projects you created and manage (where you are the payer) and projects you were invited to contribute on (where you are the payee).

This distinction is fundamental to the platform's dual-sided nature. A contractor who is both a project owner for their own team and a contributor on a client's project will face immediate confusion about which view they are in and what actions are available to them.

The opportunity: A simple visual indicator (badge, label, or sidebar group) that separates "Projects I manage" from "Projects I work on." This could also inform different default views when entering each project type.

Wireframe Priority: High

2.3 — Missing: Progressive Onboarding for New Users

The dashboard "What's New" feed is designed for existing users catching up on product updates. For a brand new user, it provides no orientation to the platform's core workflow. There is no setup checklist, no guided first-project flow, and no "here is how to get started" moment.

The opportunity: A one-time onboarding state on the dashboard that walks the user through three steps: Create your first project, Invite a team member, Log your first work entry. Once complete, the dashboard reverts to its current state. This is a low-effort, high-impact addition.

Wireframe Priority: Medium
04 — Section 3: Design and Platform Constraints

Four constraints to validate with the product team

These are observations that need validation before firm recommendations are made. They may reflect intentional product decisions.

Constraint Observation What We Need to Know
Wallet as central infrastructure The current architecture places the wallet at the centre of the payment flow. Reducing dependency on the wallet may require a UX restructure. Is the wallet the intended primary flow, or a legacy architecture decision?
Single currency per project Projects appear to be locked to a single currency at creation. This limits utility for contractors working across currency zones. Is this a technical constraint or a product decision? Is multi-currency on the roadmap?
No visible rate history per contractor The contractor profile view inside project settings only shows the current configuration, not history. Does payment history exist on the back-end? If so, surfacing it in the UI is a quick win.
Beta limitations Several flows (account management, identity verification) appear to be absent or incomplete. Which absent features are intentionally deferred vs. structurally missing?

06 — Section 5: Questions for Friday's Call

What we need to know before the second-round audit

These are the questions that need to be answered to complete a more precise second-round audit and to bring useful wireframes or flows to the follow-up session with Steve Greg.

On the ICP
  • Who is the primary user of the platform: the business owner paying contractors, the contractor receiving payment, or both equally?
  • What is the typical team size? One owner managing 1–5 contractors, or larger?
  • What is the primary device? If contractors are logging work on mobile, touch target sizing and mobile layout become more critical.
On the Platform's Direction
  • Is the stablecoin/USDC path intended to be a primary or secondary payment method? Should it be de-emphasised in the UI?
  • Are there plans to add a cross-project financial overview screen?
  • How does the platform handle projects where the user is a contributor, not an owner? Is that a live feature or on the roadmap?
  • What does the ideal onboarding journey look like? Is there a guided setup planned?
On Constraints
  • Which absent features (account management, KYC, payment method setup) are deferred Beta items vs. features that have been intentionally omitted?
  • Is payment history stored and accessible on the back-end? If so, surfacing it in the UI is a quick win.
  • What is the business model? Understanding whether revenue comes from the payer, the payee, or a transaction fee informs how we prioritise the UI for each user type.
On Design Direction
  • Are wireframes or annotated flows the preferred output for the second call, or would a written report with diagrams be more useful?
  • Is there an existing brand guide or design system we should work within?
07 — Summary: Where to Focus First

Six priorities, ranked by business impact

This is the recommended sequence for addressing the findings in this review. Priority 1 is a trust issue on the core transaction flow and should be resolved before any other design work begins.

# Area What to Fix
1 Payment confirmation Add a confirmation modal to the Pay All flow
2 Financial overview Design a cross-project financials screen
3 Project role clarity Separate owner and contributor projects in the navigation
4 Empty states Add guided empty states to all blank screens
5 Wallet hierarchy Deprioritise stablecoin, lead with bank transfer paths
6 Progressive onboarding Add a three-step first-time setup flow to the dashboard
